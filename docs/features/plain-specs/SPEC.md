# Spec view

## Summary

Open a PlainLang Module that a Session or a PR changed and read it in Lookout's main pane, as `/p-plain:page` shows it: the sections, the change since its base marked in place and a Changes card, with one switch between only what changed, the whole Module and the Module as it reads after the change. New over `/p-plain:page`: hovering a Concept defined in another Module shows that definition, so a reviewer never opens the other file to know what a word means. A Module is marked Viewed once read, so reviewing a PR's spec changes before its code is a step you can see.

## Problem

In fantastic-productive, two in three PRs change a spec: 465 of the 694 commits on `develop` from 2026-10-27 to 2026-11-04 touch `plain/`, almost always one Module each. Reading that change means `/p-plain:page` (an Artifact per Module, published from a terminal) or the raw diff in VS Code. Neither says what the words mean: 684 of `crm.plain`'s 928 Concept references are defined in another Module, mostly `productive` and `shell`, and `/p-plain:page` marks each one only as "defined in an imported module". So a reviewer reads the PR's spec with a second file open, or skips the spec and reads the code.

## Requirements

Rendering and resolution are `(test)` against fixtures (invented Modules with the shape and size of fantastic-productive's, in `server/fixtures/plain/shop/`; this repo is public, so no Productive text is copied into it); the flows across the server and the UI are `(e2e)` in a World with a real repo ([0007](../../decisions/0007-behaviour-tests-from-spec-requirements.md)); the look is `(manual)`.

### PLAIN-10 One view switch

"Only what changed" in the header and "Highlight changes" on the Changes card looked like two settings, and between them chose one of three views, plus a fourth that made no sense: only the changed clauses, unmarked, so added and removed text read alike, reached by ticking "Only what changed" (which ticks Highlight) and then unticking Highlight (`SpecView.tsx`). They were apart by accident: Highlight sat on the card from PLAIN-1.6, after `/p-plain:page`, and PLAIN-8.6 moved only the other into the header. In "Only what changed", "On this page" also kept linking to sections it hid, and following one did nothing. Now one switch in the header chooses the view, and the view opens on what changed. Decided by Dario on 2026-11-06 (clarity pass, idea 9, Plan item 48).

- [x] PLAIN-10.1 The header has one switch, a `Segmented` (DS-20) named "View", with three choices: Changes (only what changed, marked), Whole (the whole Module, its changes marked) and Clean (the Module as it reads after the change, unmarked). Each choice's tooltip is that longer wording. It replaces "Only what changed" and the Changes card's "Highlight changes", and sits after the change stepper (PLAIN-8.6); Viewed (PLAIN-4.1) is last, after a divider (DS-18.5's: a 1 px line in `border`, 16 px tall, 4 px either side). (test)
- [x] PLAIN-10.2 A Module with a change (one PLAIN-8.5 counts) opens on Changes whenever it's opened: from DIFF's list, from Work's Specs, from a link in another Module, or after a reload. The view you choose holds while the view stays open, through its reads (PLAIN-1.7), and is kept with the history entry as its scroll position is (PLAIN-2.5), so Back returns to a Module in the view you left it in. (test)
- [x] PLAIN-10.3 A Module with no change opens on Clean, with no switch; so does one whose text differs from its base where no clause, note, definition or description does, which says so under its header ("Its text differs from the base, but no clause, note or definition does"). When a read gives a Module its first change, the switch appears on the view you're reading (Clean); when a read takes its last change away, the view becomes Clean and the switch goes. (test)

## Non-goals

- **Talking back to the Session from the view** (select a clause, "Ask the Session about this"). In the Backlog.
- **Editing a Module.** "Open in VS Code" (PLAIN-3.1) is where you edit.
- **Comments on clauses**, or posting a review to GitHub.
- **Ability-key links** (`/p-plain:page`'s `--ability-url`): Lookout doesn't know a repo's catalogue URL. A key is explained from the Checkout's own catalogue instead (PLAIN-7.5).
- **Explaining a rule's conditions themselves** (what a permission, fact or plan feature means): a card names them as the catalogue does.
- **A summary of a change in plainer words**: dropped by Dario on 2026-11-09 for PLAIN-11's examples, since a summary reads as one more text to check.
- **A picture of the old app** (Ember): dropped by Dario on 2026-11-09. Lookout can't take one by itself (the old app needs a login, and Ember's tests name no `§` and run after a build of minutes); PLAIN-12 checks a port in words instead.
- **Checklist rows that name no `§`** (PLAIN-12.2): matching them to a spec would be Claude's guess; a port doc that names its `§` is checked.
- **Running a Playwright test that names no changed spec**, or the whole suite: PLAIN-11 shows a change, it doesn't test the branch.
- **Showing part of a folded run** (GitHub's 20 lines at a time): a run opens whole (PLAIN-10.6), and Whole is one choice away.
- **Remembering the view across Modules or reloads**: every Module with a change opens on Changes (PLAIN-10.2).
- **Gating a PR on Viewed** (PLAIN-4.4). A gate belongs in `/p-dev:open-pr` if anywhere.
- **Checking a Module**: syntax errors, Concept collisions, missing `required_concepts`. That is `/p-plain:plain`'s and codeplain's job.
- **Fetching provider Modules** from other repos (fantastic-productive's `providers.json`). PLAIN-2.4 says they're missing.
- **Publishing** the view as an Artifact or a Share. `/p-plain:page` still does that, for a reviewer outside Lookout.
- **Moving the resolver into p-plain or a CLI.** Lookout is its only consumer today (0010); it moves when `/p-plain:page` wants the popover too.

## Technical approach

- **Parser and diff** in `shared/plain/`, in TypeScript, ported from p-plain 0.6.1's `page-template.html` (its `parse`, `lcs`, `wordDiff`, `diffContainer`), with tests on invented Modules shaped and sized like fantastic-productive's. The output is a tree of sections and clauses, each with its state (`same`, `added`, `removed`, `changed` with its old text).
- **Resolution** on the server (`server/plain.ts`): read the Module and its base with `git show <ref>:<path>` (the working tree for the head of a Checkout), walk `import` transitively and `requires` one level for `exported_concepts`, and answer the Module's tree with a map of every visible Concept to `{ module, text, baseText | null, state }`. One endpoint, `GET /api/plain?checkout=&path=`, answers the lot; the client renders it.
- **Checkout ids** come from DIFF's answer (each candidate Checkout gets an opaque id for its path); a PR is named by its repo and number, which the server maps to a clone it knows (`server/plain-prs.ts`), so the URL never carries a path (PLAIN-6.1).
- **Viewed** in `~/.lookout/plain-viewed.json`, as `{ key: { at } }`, written atomically, read once at start.
- **Work** (slice 2) gets the PR's base branch from `tb-pr` 0.4.0's `base_branch` (confirmed in its `--json`); for a PR Work hasn't read, `gh pr view --json baseRefName`, through the repo flag.
- **References** (PLAIN-7) in `server/plain.ts` and `server/abilities.ts`: the `.plain` files under the Module's folder are listed (`git ls-files` at the working tree, reused for 15 s so a view's polls don't rescan the tree; `git ls-tree` at a commit, cached per commit) and only the Modules holding a referenced `§` are parsed; the catalogue files are listed the same way and read with a small tokenizer for object literals (strings, keys, arrays, a same-file constant), never evaluated. The answer gains `specs` (another Module's referenced specs, at head and base) and `abilities` (each key's entry at head and base, and those its rules name).
- **The view** (PLAIN-10): one state, `view: 'changes' | 'whole' | 'clean'`, replaces `highlight` and `onlyChanged`, and is kept beside the scroll position under the history entry's `lookoutEntry`. A fold line is one component for every level (clauses, acceptance tests, notes, definitions, specs, a section's body), keyed by where it is and every item it holds (a spec's id, a clause's text), hashed, so a read that keeps the run keeps it open and a read that changes it closes it. A fold line names the anchors it holds (`data-holds`), so a link's target that is folded is found by its id before the scroll, and its run opened first.
- **Examples** (PLAIN-11, 12) in `server/plain-examples.ts`: find the groups from the compared tree (`shared/plain.ts`), their Playwright tests by `git grep` for `§` titles in the Checkout's tracked spec files, the config by its `testDir` literal; run `node_modules/.bin/playwright test -c <config> --trace on --workers 1 --retries 0 --reporter line --output <run folder> <files> --grep <titles>` (flags, not a wrapper config: a wrapper elsewhere would resolve the config's relative paths, `testDir`, `webServer`'s and setup files, against its own folder) through `res run --prio live --` when `res` is found (`server/res.ts`'s `resolveResBin`), else directly, in its own process group (the Runner), cancelled with it. Each test's `trace.zip` is unpacked with `unzip -p` (macOS has it): its `context-options` line's `title` names the test (`<file>:<line> › <title>`), and its `*.trace` lines give the `expect` steps (`before` with `method: 'expect'`, `after` with its `endTime`) and the `screencast-frame` events (`timestamp`, `file`) on one clock, so a check's frame is the last one at or before its end. The words come from `oneShotArgs` (`server/summarizer.ts`) with this feature's schema and prompt; the quote check (PLAIN-11.8) runs on the answer before it's kept. Port docs (PLAIN-12) are read with `git ls-files knowledge/port` and file reads at the working tree. Kept as `~/.lookout/plain-examples/<key>/answer.json` and `<frame>.jpg`, the key a hash of the repo's common directory, the Module's path and the spec id; served by `GET /api/plain/examples?…` (the answer) and `GET /api/plain/examples/frame?…` (a JPEG, by its name in the answer).
- **Building blocks**: git and the existing Fleet `diff` answer; `tb-pr` for slice 2. No new CLI (0005, 0010).
- Decisions: [0005](../../decisions/0005-building-blocks-live-outside-lookout.md), [0010](../../decisions/0010-single-consumer-rules-stay-with-the-consumer.md), [0009](../../decisions/0009-one-design-system-guarded-by-tests.md).

### Key decisions

- **Lookout renders it, on its own design system, not `page.mjs` in an iframe** (Dario, 2026-11-04): an iframe can't share Lookout's keyboard, Viewed marks or themes, and changing `page.mjs` waits on its owners' reviews.
- **The resolver stays in Lookout** (Dario, 2026-11-04): Lookout is its only consumer (0010); it moves to a CLI or p-plain when a second one wants it.
- **Two slices: a Session's changed files first, Work's PRs second** (Dario, 2026-11-04): your own PRs come from a Session whose Checkout DIFF already knows; a Review request has no Checkout and needs a fetch.
- **The main pane, at its own URL** (Dario, 2026-11-04): a 1,200-line Module needs the width, and a URL gives reload, new tab and Back.
