# Spec view

## Summary

Open a PlainLang Module that a Session or a PR changed and read it in Lookout's main pane, as `/p-plain:page` shows it: the sections, the change since its base marked in place and a Changes card, with one switch between only what changed, the whole Module and the Module as it reads after the change. New over `/p-plain:page`: hovering a Concept defined in another Module shows that definition, so a reviewer never opens the other file to know what a word means. A Module is marked Viewed once read, so reviewing a PR's spec changes before its code is a step you can see. On a press, Claude also rewrites the changed specs in simple words beside them, and every paragraph cites the clauses it comes from (PLAIN-14).

## Problem

In fantastic-productive, two in three PRs change a spec: 465 of the 694 commits on `develop` from 2026-10-27 to 2026-11-04 touch `plain/`, almost always one Module each. Reading that change means `/p-plain:page` (an Artifact per Module, published from a terminal) or the raw diff in VS Code. Neither says what the words mean: 684 of `crm.plain`'s 928 Concept references are defined in another Module, mostly `productive` and `shell`, and `/p-plain:page` marks each one only as "defined in an imported module". So a reviewer reads the PR's spec with a second file open, or skips the spec and reads the code.

## Requirements

Rendering and resolution are `(test)` against fixtures (invented Modules with the shape and size of fantastic-productive's, in `server/fixtures/plain/shop/`; this repo is public, so no Productive text is copied into it); the flows across the server and the UI are `(e2e)` in a World with a real repo ([0007](../../decisions/0007-behaviour-tests-from-spec-requirements.md)); the look is `(manual)`.

### PLAIN-10 One view switch

"Only what changed" in the header and "Highlight changes" on the Changes card looked like two settings, and between them chose one of three views, plus a fourth that made no sense: only the changed clauses, unmarked, so added and removed text read alike, reached by ticking "Only what changed" (which ticks Highlight) and then unticking Highlight (`SpecView.tsx`). They were apart by accident: Highlight sat on the card from PLAIN-1.6, after `/p-plain:page`, and PLAIN-8.6 moved only the other into the header. In "Only what changed", "On this page" also kept linking to sections it hid, and following one did nothing. Now one switch in the header chooses the view, and the view opens on what changed. Decided by Dario on 2026-11-06 (clarity pass, idea 9, Plan item 48).

- [x] PLAIN-10.1 The header has one switch, a `Segmented` (DS-20) named "View", with three choices: Changes (only what changed, marked), Whole (the whole Module, its changes marked) and Clean (the Module as it reads after the change, unmarked). Each choice's tooltip is that longer wording. It replaces "Only what changed" and the Changes card's "Highlight changes", and sits after the change stepper (PLAIN-8.6); Viewed (PLAIN-4.1) is last, after a divider (DS-18.5's: a 1 px line in `border`, 16 px tall, 4 px either side). (test)
- [x] PLAIN-10.2 A Module with a change (one PLAIN-8.5 counts) opens on Changes whenever it's opened: from DIFF's list, from Work's Specs, from a link in another Module, or after a reload. The view you choose holds while the view stays open, through its reads (PLAIN-1.7), and is kept with the history entry as its scroll position is (PLAIN-2.5), so Back returns to a Module in the view you left it in. (test)
- [x] PLAIN-10.3 A Module with no change opens on Clean, with no switch; so does one whose text differs from its base where no clause, note, definition or description does, which says so under its header ("Its text differs from the base, but no clause, note or definition does"). A new Module's Changes and Whole show the same, every clause added. A deleted Module opens on Changes, and its Clean is disabled, with the tooltip "Deleted in this branch". When a read gives a Module its first change, the switch appears on the view you're reading (Clean); when a read takes its last change away, the view becomes Clean and the switch goes. (test)
- [x] PLAIN-10.4 Clean reads as a Module with no change: no marks, no Changes card, no change stepper, no rail (PLAIN-8.5), and "On this page" lists every spec, unmarked (PLAIN-8.2). A removed clause isn't there, a rewritten one reads as it does now. "Changed since you viewed it" (PLAIN-4.3) and a failed fetch (PLAIN-5.4) still show. (test)
- [x] PLAIN-10.5 Changes shows each change with what holds it: a changed clause with its unchanged parents, and a changed spec with its heading. "On this page" lists, as in Whole, the sections and the changed specs, so every entry lands on a heading. (test)

  - every number in it is in its cited clauses, as digits or as two to twelve in words; "one" doesn't count as a number said, since it's too often a pronoun ("the one you picked"); a number in a code span, a `§` id, a task, issue or PR's number ("Task 20900640", "#3719") or a date doesn't count. A minus sign is the number's: a paragraph's -2 isn't a clause's 2, though "2 days earlier" keeps a clause's -2;
  - it has no em dash and none of anti-ai-editor's banned words and patterns, kept as a list in the code (the skill as Dario pointed to it on 2026-11-11). A word or an em dash inside a quote (a field that reads "—", on PR #3719), or a word its cited clauses use themselves ("navigate" in a clause about navigating), is the spec's, not the writer's.

  A paragraph that fails is dropped, and its clauses count as left out (PLAIN-14.5). Then each cited clause's and note's numbers must be in the paragraphs citing it, between them, "one" keeping its 1: a clause told in two paragraphs needs its numbers only once. A clause's "one" is a number only in a limit ("at most one", "only one", "exactly one", "more than one"). A clause they don't say whole counts as left out too, though its paragraphs show (found on PR #3719: a check per paragraph threw away a correct paragraph that told half of a clause). A term whose name isn't in its cited clauses, or whose phrase isn't in the paragraph, isn't kept as a term; the paragraph is, since its words are checked as words. A title that fails the word or quote check is the spec's gist instead. A lead line is dropped when it cites no changed spec, or fails the quote, word or dash check, and the lead is dropped without its "What changes" line. A block left with no paragraph says "Couldn't be simplified: <the first check it failed>".

## Non-goals

- **Talking back to the Session from the view** (select a clause, "Ask the Session about this"). In the Backlog.
- **Editing a Module.** "Open in VS Code" (PLAIN-3.1) is where you edit.
- **Comments on clauses**, or posting a review to GitHub.
- **Ability-key links** (`/p-plain:page`'s `--ability-url`): Lookout doesn't know a repo's catalogue URL. A key is explained from the Checkout's own catalogue instead (PLAIN-7.5).
- **Explaining a rule's conditions themselves** (what a permission, fact or plan feature means): a card names them as the catalogue does.
- **Simplifying an unchanged spec, or a whole Module** (Dario, 2026-11-11: only the changed parts). A Module like `crm.plain` holds 211 specs, too many for one run, and an unchanged spec isn't what a review reads. This replaces the Non-goal of 2026-11-09, "a summary in plainer words", dropped then because a summary reads as one more text to check. PLAIN-14 answers that worry with receipts: every paragraph cites its clauses, and code checks it before it shows.
- **Simplifying on its own**, on opening a Module or on a read (PLAIN-14.1). A small change needn't be simplified, and a run costs money.
- **Editing the simplified version**, or asking Claude about a paragraph.
- **A picture of the old app** (Ember): dropped by Dario on 2026-11-09. Lookout can't take one by itself (the old app needs a login, and Ember's tests name no `§` and run after a build of minutes); PLAIN-12 checks a port in words instead.
- **Checklist rows that name no `§`** (PLAIN-12.2): matching them to a spec would be Claude's guess; a port doc that names its `§` is checked.
- **Running a Playwright test that names no changed spec**, or the whole suite: PLAIN-11 shows a change, it doesn't test the branch.
- **Showing part of a folded run** (GitHub's 20 lines at a time): a run opens whole (PLAIN-10.6), and Whole is one choice away.
- **Remembering the view across Modules or reloads**: every Module with a change opens on Changes (PLAIN-10.2).
- **Gating a PR on Viewed** (PLAIN-4.4). A gate belongs in `/p-dev:open-pr` if anywhere.
- **Checking a Module**: syntax errors, Concept collisions, missing `required_concepts`. That is `/p-plain:plain`'s and codeplain's job.
- **Fetching provider Modules** from other repos (fantastic-productive's `providers.json`). PLAIN-2.4 says they're missing.
- **Publishing** the view as an Artifact or a Share. `/p-plain:page` still does that, for a reviewer outside Lookout.
- **Moving the resolver into p-plain or a CLI.** Lookout is its only consumer today (0010); it moves when `/p-plain:page` wants the popover too.

## Technical approach

- **Parser and diff** in `shared/plain/`, in TypeScript, ported from p-plain 0.6.1's `page-template.html` (its `parse`, `lcs`, `wordDiff`, `diffContainer`), with tests on invented Modules shaped and sized like fantastic-productive's. The output is a tree of sections and clauses, each with its state (`same`, `added`, `removed`, `changed` with its old text).
- **Resolution** on the server (`server/plain.ts`): read the Module and its base with `git show <ref>:<path>` (the working tree for the head of a Checkout), walk `import` transitively and `requires` one level for `exported_concepts`, and answer the Module's tree with a map of every visible Concept to `{ module, text, baseText | null, state }`. One endpoint, `GET /api/plain?checkout=&path=`, answers the lot; the client renders it.
- **Checkout ids** come from DIFF's answer (each candidate Checkout gets an opaque id for its path); a PR is named by its repo and number, which the server maps to a clone it knows (`server/plain-prs.ts`), so the URL never carries a path (PLAIN-6.1).
- **Viewed** in `~/.lookout/plain-viewed.json`, as `{ key: { at } }`, written atomically, read once at start.
- **Work** (slice 2) gets the PR's base branch from `tb-pr` 0.4.0's `base_branch` (confirmed in its `--json`); for a PR Work hasn't read, `gh pr view --json baseRefName`, through the repo flag.
- **References** (PLAIN-7) in `server/plain.ts` and `server/abilities.ts`: the `.plain` files under the Module's folder are listed (`git ls-files` at the working tree, reused for 15 s so a view's polls don't rescan the tree; `git ls-tree` at a commit, cached per commit) and only the Modules holding a referenced `§` are parsed; the catalogue files are listed the same way and read with a small tokenizer for object literals (strings, keys, arrays, a same-file constant), never evaluated. The answer gains `specs` (another Module's referenced specs, at head and base) and `abilities` (each key's entry at head and base, and those its rules name).
- **The view** (PLAIN-10): one state, `view: 'changes' | 'whole' | 'clean'`, replaces `highlight` and `onlyChanged`, and is kept beside the scroll position under the history entry's `lookoutEntry`. A fold line is one component for every level (clauses, acceptance tests, notes, definitions, specs, a section's body), keyed by where it is and every item it holds (a spec's id, a clause's text), hashed, so a read that keeps the run keeps it open and a read that changes it closes it. A fold line names the anchors it holds (`data-holds`), so a link's target that is folded is found by its id before the scroll, and its run opened first.
- **Examples** (PLAIN-11, 12) in `server/plain-examples.ts`: find the groups from the compared tree (`shared/plain.ts`), their Playwright tests by `git grep` for `§` titles in the Checkout's tracked spec files, the config by its `testDir` literal; run `node_modules/.bin/playwright test -c <config> --trace on --workers 1 --retries 0 --reporter line --output <run folder> <files> --grep <titles>` (flags, not a wrapper config: a wrapper elsewhere would resolve the config's relative paths, `testDir`, `webServer`'s and setup files, against its own folder) through `res run --prio live --` when `res` is found (`server/res.ts`'s `resolveResBin`), else directly, in its own process group (the Runner), cancelled with it. Each test's `trace.zip` is unpacked with `unzip -p` (macOS has it): its `context-options` line's `title` names the test (`<file>:<line> › <title>`), and its `*.trace` lines give the `expect` steps (`before` with `method: 'expect'`, `after` with its `endTime`) and the `screencast-frame` events (`timestamp`, `file`) on one clock, so a check's frame is the last one at or before its end. The words come from `oneShotArgs` (`server/summarizer.ts`) with this feature's schema and prompt; the quote check (PLAIN-11.8) runs on the answer before it's kept. Port docs (PLAIN-12) are read with `git ls-files knowledge/port` and file reads at the working tree. Kept as `~/.lookout/plain-examples/<key>/answer.json` and `<frame>.jpg`, the key a hash of the repo's common directory, the Module's path and the spec id; served by `GET /api/plain/examples?…` (the answer) and `GET /api/plain/examples/frame?…` (a JPEG, by its name in the answer). A PR's run (PLAIN-11.15) gets its worktree from `server/plain-worktrees.ts`: `git worktree list --porcelain -z` in the clone for one at the head with an empty `git status --porcelain`, else `git worktree add --detach` under `~/.lookout/plain-worktrees/`, removed with `git worktree remove --force` and then `rm` (which never follows a link out); the dependencies by `cp -c` from a checkout whose lockfile is byte-equal, else `npm ci` or `pnpm install --frozen-lockfile`. The press answers before any of it, so its failures are the run's (PLAIN-11.13's Alert).
- **Proof shots** (PLAIN-13) in `server/plain-shots-render.mjs`, run with the Checkout's Node: it loads the test runner's own `playwright-core` (the package that owns the CLI `.bin/playwright` runs, npm's link or the file pnpm's shell shim names, then `playwright` → `playwright-core`, the copy the tests ran with, though the Checkout's `@playwright/test` may be another version; without a CLI, from the Checkout's `@playwright/test`; fantastic-productive also has a newer one at the top of `node_modules`; only a copy inside the Checkout counts, since Node also looks in global folders), serves its `lib/vite/traceViewer` and the run's `trace.zip` files on 127.0.0.1, registers the viewer's service worker from its `index.html`, and opens `snapshot/<callId>?trace=<zip>&phase=after` in a context at the trace's viewport and `deviceScaleFactor: 2`, every other host refused; 10 s a snapshot, and past 75 s the rest are answered as not rendered, so Lookout's 90 s cut-off never loses the shots that did. The marked element is `[__playwright_target__]`; the viewer outlines it inline (`2px solid #006ab1`, a blue fill), which the script clears before the screenshot. An absence check's container is found with the check's own selector, less its last part, through `page.locator`. Tried on 2026-11-09 against a real trace of §16.50.1: about 40 ms a snapshot after a 1.5 s start, every check's after-snapshot marked, `toHaveCount(0)` unmarked. `server/plain-examples.ts` reads each check's call id, selector and the page steps since the check before from the trace (PLAIN-11.5), names the steps (PLAIN-13.4), and sends the chosen checks to the script after the writing run.
- **Simplified version** (PLAIN-14) in `server/plain-simplify.ts`.
  - **Input:** the groups come from the compared tree (`shared/plain.ts`, which gains each clause's number), and the Concept and Ability key texts from the read's answer (PLAIN-2.6, 7.9).
  - **Run:** one `oneShotArgs` run with this feature's schema and prompt.
  - **Checks:** in `server/plain-simplify.ts`, beside the run, as the examples' quote check is in `server/plain-examples.ts`: clause numbers, quotes (PLAIN-11.8's function), numbers, terms, the banned list and the em dash, and the Flesch score, with syllables estimated from vowel groups, as the skill allows without `textstat`. The numbering is `numberSpec` in `shared/plain.ts`, so the server's numbers are the view's.
  - **Storage and endpoints:** kept as `~/.lookout/plain-simple/<key>/answer.json`, keyed as examples are (PLAIN-11.12). Served by `GET /api/plain/simple`, run by `POST /api/plain/simple` and its `…/cancel`, with a run registry of its own built as PLAIN-11.13's (one run per Module, found by the press's source and path for Cancel) and the same wait.
  - **The view:** in `SpecView.tsx`, each row is one grid (`minmax(0, 34fr) 1px minmax(0, 30fr)`, at most 68rem wide), so a block sits level with its spec without measuring. The side's width rule measures the main pane with a ResizeObserver (64rem), not a container query: whether a block swaps in place changes what is rendered, not only how it's styled. The lighting is one state, `{ kind, key }`, that maps paragraphs to clause ids both ways.
- **Building blocks**: git and the existing Fleet `diff` answer; `tb-pr` for slice 2. No new CLI (0005, 0010).
- Decisions: [0005](../../decisions/0005-building-blocks-live-outside-lookout.md), [0010](../../decisions/0010-single-consumer-rules-stay-with-the-consumer.md), [0009](../../decisions/0009-one-design-system-guarded-by-tests.md).

### Key decisions

- **Lookout renders it, on its own design system, not `page.mjs` in an iframe** (Dario, 2026-11-04): an iframe can't share Lookout's keyboard, Viewed marks or themes, and changing `page.mjs` waits on its owners' reviews.
- **The resolver stays in Lookout** (Dario, 2026-11-04): Lookout is its only consumer (0010); it moves to a CLI or p-plain when a second one wants it.
- **Two slices: a Session's changed files first, Work's PRs second** (Dario, 2026-11-04): your own PRs come from a Session whose Checkout DIFF already knows; a Review request has no Checkout and needs a fetch.
- **The main pane, at its own URL** (Dario, 2026-11-04): a 1,200-line Module needs the width, and a URL gives reload, new tab and Back.
- **The base is DIFF's Branch point, imports from the same tree** (Dario, 2026-11-04): the view and DIFF's count never disagree, and a Concept's popover shows the definition as this branch has it.
- **Viewed is explicit and persisted** (Dario, 2026-11-04): opening a long Module isn't reading it, and a review spans reloads; DIFF-3.7's marks, kept until a reload, are too short-lived for that.
- **Reading and stepping (PLAIN-8): option A of three drawn, with B's change stepper** (Dario, 2026-11-05, https://claude.ai/artifact/QtSAwRw2w1WjkjFHcfz5eN): the column centred as the chat's, the outline on its right, bars instead of words. C, the outline as a sidebar-style panel, took the most width and added a fourth column.
- **A change is a bookmark** (Dario, 2026-11-05): "On this page" is the Module's structure, which the chat doesn't have; stepping through changes is what the chat's bookmarks do, so it is the same rail and the same `[`/`]`, not a third kind of navigation with its own keys.
- **Reading a Module (PLAIN-9): ideas 1 and 2 of three drawn, nothing from the third** (Dario, 2026-11-05, https://claude.ai/artifact/1B7FmUEyqXzR2WoUGBmQrD). Measured on `crm.plain` before it: 14 px text at about 111 characters a line, against 45 to 75 in the research (Bringhurst; Dyson and Haselgrove; Nanavati and Bias, 2005) and WCAG 1.4.8's 80; and a spec's heading the size of its text, so one spec ran into the next. Idea 3, quieter terms and folded removals, was left out: underlining a term only at its first use, and folding removed clauses and a rewrite's old words, hide what a review is for.
- **Two type steps of its own, not a bigger `prose`** (Dario, 2026-11-05): the chat stays at 14 px; a Module of 1,200 lines is read like a book, not scanned like a row. DS-1.1 amended.
- **The column's left edge stays the chat's** (Dario, 2026-11-05): the text stops short of the 48rem column's right edge rather than a narrower column centred on its own.
- **42rem, not 36rem** (Dario, 2026-11-05, after seeing it): 36rem (74 characters a line, measured on `crm.plain`) left the text small in the middle of a wide pane. 42rem measures 86, past the research's 75 and WCAG 1.4.8's 80, traded for a fuller column; the gap before "On this page" is 6rem instead of 12.
- **A rewritten clause's colour is `muted-foreground`** (2026-11-05): DS-2.5's diff family has added and removed only, and a third hue would read as a Status (DS-3.6); the words inside it carry the green and red.
- **References before summaries** (Dario, 2026-11-06): what makes a Module hard to read is mostly what a clause points at, a `§` list or a gate's key, not its words; explaining those from the repo's own text costs no AI and can't be wrong. A paraphrase per clause (the first idea for PLAIN-7) doubles the reading and can drop a condition. Summaries and the port check follow (Plan item 38).
- **One switch, opening on Changes** (Dario, 2026-11-06, the clarity pass's idea 9): the two boxes were one choice split in two by accident, and one of their four combinations hid whether text was added or removed. Changes, Whole and Clean, with the longer wording in tooltips; Viewed stays in the header, last, behind a divider, since it's the file's review state rather than a way to view it, as on GitHub.
- **Changes keeps context one click away** (PLAIN-10.5, 10.6): what it hides leaves a line saying what's there, at every level, so a reviewer sees the Module's shape and every link lands. On PR #3426 that is two lines between specs (4 before §16.3.1, 165 between it and §16.43) instead of 169 specs to scroll past.
- **Clean reads as an unchanged Module** (PLAIN-10.4): no card, stepper or rail, since it's for reading the spec as it will be after the merge.
- **What gives way in a narrow header** (PLAIN-10.7): measured at a 480 px main pane on 2026-11-06, today's header fills its 440 px (Back 38, name 77, stepper 118, "Changed only" 98, Viewed 61, four 12 px gaps). The switch is about 162 px (its words 51, 36 and 33 px in `meta` medium, with their padding and track) and the divider 13 with its gap, 77 px more. Viewed's word gives about 45 px and the name the rest; the switch and the stepper's count stay, since the count is the only place you are when the rail is hidden in a narrow pane.
- **No key for the switch** (PLAIN-10.8): the view opens on Changes, so switching is rare; `C` and `W` are taken (Library's Copy, the Work panel), and number keys would be the only ones in Lookout.
- **Pictures from the repo's own Playwright tests** (Dario, 2026-11-09, PLAIN-11): 1,824 of fantastic-productive's 1,967 functional specs (93%) have a test whose title starts with their `§`, and those tests run the real app against mocks, with no login. One ran in 7 to 8 s through `res`, and its trace keeps a frame at every check, so the picture is the moment a check describes ("Mark as won?"), not the test's end (the board after Cancel). Only 3 of the last 30 merged PRs carried any image, and a screenshot of the running app needs a login and shows the app before the change. The catch, said in the card (`shows`): a spec's test may show another case than the change (slice 4's tests show a sales deal, where nothing asks), so the picture says which view the spec is about and the example says what it does.
- **Claude writes the example, under rules and a check** (Dario, 2026-11-09, PLAIN-11.7, 11.8): the run reads no CLAUDE.md or style guide (`--setting-sources ''`), so the writing rules are in its prompt, and quoting a label the spec doesn't have, the worst way an example can mislead, is caught by code rather than trusted to the prompt.
- **On a press, once per Module** (Dario, 2026-11-09): tests use the machine's CPU and the run costs money, as a Topic summary's does (TOPIC-11.1).
- **A port is checked by its own rows** (Dario, 2026-11-09, PLAIN-12): rows that name the `§` (85% of 537 capability-table rows, 8% of 2,345 checklist rows across 112 port docs), shown as written, with Claude's verdict beside them; a ported Module's group that no row names is said, since that is the gap a reviewer looks for.
- **No gate on opening a PR** (Dario, 2026-11-04): Lookout can't enforce it; the harness rule puts gates in the CLIs and hooks.
- **A simplified version beside the spec, on its own press** (Dario, 2026-11-11, PLAIN-14). Dario found long specs still hard to read with proof shots and a storyboard, and asked for a side view of a simplified spec. Three boards were drawn: In short in the Changes card, the two columns side by side, and a narrow pane where it swaps in place. Dario chose side by side, because it keeps both texts in view, with margins so it isn't crammed. The narrow board is its fallback under 64rem.
- **Receipts answer "one more text to check"** (2026-11-11). That was why a summary was dropped on 2026-11-09. Now every paragraph names its clauses, hovering lights them, and code drops a paragraph that adds a number, a quote or a term its clauses don't have, so a reader checks a claim at a glance rather than rereading the spec. A left-out clause is shown, not hidden.
- **Reading ease is a floor for the simplified text, not a measure of the spec** (2026-11-11). `crm.plain`'s specs already score about 62. Their cost is jargon and nesting, which a reading-ease score doesn't see, so the side explains terms (PLAIN-14.7) and turns nesting into paragraphs, rather than only shortening sentences.
- **Named Simplified, not Plain** (2026-11-11). In a view of `.plain` Modules, "Plain" names the file format, and Dario's word for it was "simplified".
