# Session view

## Summary

The main pane for the Session selected in the sidebar. It shows the conversation as a chat built from the Transcript, a terminal preview, a composer to type into the Session, and buttons to answer what it's waiting on. Together with SIDE, it lets you follow and steer a Session without opening a terminal.

## Problem

Selecting a Session in SIDE shows only a placeholder. To see what an agent did, or to reply, you still have to find its terminal. When it Needs you, the question it's asking is only visible in that terminal.

## Requirements

### VIEW-1 Chat from the Transcript

The selected Session's conversation, read from its Transcript. Works for every Session Fleet lists, Controllable or not (Codex: see Known gaps (fork)).

- [x] VIEW-1.17 A file path in your prompts (slash commands included), in a reply's prose and inline code, and on tool-call lines is a link once the server says the file exists (VIEW-1.18). A relative path is the Session's folder's (its cwd as Fleet lists it); an absolute one is used as is. A path has no spaces and its file name ends in a common code or doc extension, optionally followed by `:line` or `:line:col` (a range, `:12-20`, opens at its first line). Version numbers, abbreviations such as `e.g.`, a word that ends a sentence, a `~` or `$VAR` path, a path inside a web address, linked or not (VIEW-1.12), and one in a code block stay text. The text reads and copies as before. (test)
- [x] VIEW-1.18 Whether a path is a file is the server's answer: a read-only check that takes a Session and at most 100 paths, and answers, for each, only whether it's a file and, if it is, its absolute path. ## Technical approach

- **Building blocks.** Fleet's CLI with `--json` ([0004](../../decisions/0004-fleet-cli-as-session-layer.md)), from the fork `dafilipaj/fleet` ([0006](../../decisions/0006-run-a-fork-of-fleet.md)). *Target* is the `session_id` prefix or the pid.
  - **Available now** (checked in Fleet 38a461c's source):
    - `fleet --local send --json --require-empty -- <target> <text>` types the text and submits it (VIEW-3). Text with line breaks goes in as a tmux paste, so they survive; a single line is typed. The `--` keeps text that starts with `-` from being read as an option. Lookout's target is the full `session_id`, or the pid for a Codex Session without one.
    - **Held sends (VIEW-3.7; fork `lookout` e0d4612, docs/cli.md "Sending").** Under the Session's typing lock, `send` reads the input box off the screen once and types only into an empty one. Without `--require-empty`, a box it can't find or read is typed into anyway, with a warning: that's how `/usage`'s panel, which only Esc closes, took Dario's next message. So Lookout always passes `--require-empty`, never `--force`. Held: exit 3 with `{ok: false, host, kind: "send_held", reason, error, input?}`, `reason` one of `text`, `prompt`, `no_input_box`, `unreadable`; sent: exit 0 with `{ok: true, …}`.
      - **In Lookout (`server/viewer.ts` `send`):** a held send is a 409, `{error, field: null, kind: "send_held", reason}`. The message is Lookout's own, by reason (VIEW-6.6's words): `text` → "The Session's input box already holds text, so nothing was sent. Send or clear it in the terminal, then try again."; `prompt` → "The Session is waiting on a prompt, so nothing was sent. Answer it, then try again."; `no_input_box` → "The Session's input box isn't on screen (a panel, a menu or the transcript view is open), so nothing was sent. Press Esc to close it, then try again."; `unreadable` → "Fleet can't read the Session's input box, so nothing was sent. Send it from the terminal instead."; any other reason → "Fleet held the message, so nothing was sent. Check the terminal." with `reason` null. `input` is whatever the person typed or pasted there, a secret maybe: Lookout never reads past `kind` and `reason`, so it's never forwarded, logged or put in a message, and Fleet's `error` isn't shown either. Exit 0 is sent, whatever stdout holds. A Fleet without the flags (clap's "unexpected argument") types nothing: 501, "This Fleet can't check the Session's input box before sending. Update the Fleet fork." Other failures stay as before (Fleet's stderr line, tmux reworded).
      - **In the tab:** a held send is a failed send (VIEW-3.4): the composer keeps the text, the error shows above the box, the dimmed message goes (VIEW-1.13). The tab keeps the reason with the error (`sendErrors` holds `{message, held}`), so while the Esc button shows (VIEW-4.5), `no_input_box` and `prompt` get the pointer (UX) at render time; it goes when the button does.
      - **Blanks before a slash command (VIEW-3.8).** Claude Code runs a slash command only when `/` is the box's first character; ` /model sonnet` is a prompt, which the model answers as if it had switched (Dario's Session on 2026-10-21 stayed on Haiku). `asSent` (`shared/message.ts`) drops the blanks before a leading `/`, so the server sends what the tab's copy matching (VIEW-1.13) already counted as a command. Blanks left in Claude Code's own box do the same: it draws nothing for them, and Fleet up to ec4ed52 read such a box as empty, so `send` typed the command behind them (reproduced against Claude Code 2.1.306). The fork change on branch `fix/send-slash-commands` (not yet committed, so not in the pin) reads the terminal's cursor too: past where the box's text starts, the blanks before it are `text`, and the send is held (VIEW-3.7's `text`).
      - **Not covered:** "Escape, then wait about a second before `send`" (docs/cli.md, Limits): Claude Code puts a prompt Stop interrupted back in the box only once the turn has stopped, so a send within about a second of Stop's Esc can still read the box empty and join that prompt.
    - **Targets aren't exact-only in Fleet.** `resolve_in` tries an exact match first, but a target nothing matches exactly falls through to prefix, substring and characters-in-order matching on titles. So the pid of a Session that just exited could match another Session's title, and the text would be typed there. Interim guard in Lookout: right before a send or peek with a pid target, the server runs a fresh `fleet list --json` and goes ahead only if that pid is still listed with the same Harness; otherwise it refuses ("no longer running"). A `session_id` target goes ahead only when the latest list has it. The fork has since added exact targets (`id:<session_id>`, `pid:<n>`, never falling through); `close`, `answer` and `keys` (VIEW-4) use them, and keep the guard as well. Send and peek move to them when they're next worked on.
    - `fleet --local peek --lines 40 -- <target>` prints the terminal's last lines (VIEW-2). The text is shown as is, never parsed, so it doesn't conflict with 0004. Known gaps, both for a raw peek mode in the fork:
      - Peek's first line is Fleet's own header, `▼ <title> (tmux, <status>) — <dir>`, so the preview names tmux, which 0001 keeps out of the UI. Lookout doesn't strip it, since that would be parsing.
      - Peek cuts each line to the terminal width minus 2. A detached tmux Session is 80 columns wide, which Claude Code and Codex fill anyway, but an iTerm2-backed Session loses most of each long line. VIEW-2.1 is verified for tmux Sessions.
    - Before sending, the server checks that Fleet's latest list has the Session and that it's Controllable, and caps a message at 100,000 characters (413 as a field error). In a one-line message a tab becomes four spaces, since one line is typed and a tab would be a keypress; multi-line text is pasted, so its tabs arrive intact (Makefiles, Go, TSV). Other control characters are refused, since typed they'd be keypresses (Esc, Ctrl-C). Fleet errors that mention tmux are reworded ("the Session host refused the message"), per 0001. It passes Fleet the same cleaned environment as LAUNCH.
  - **Added in the fork** (built; VIEW-1 and VIEW-4 use them):
    - **`fleet messages <target> --json`** (VIEW-1). A Rust port of Fleet's own `web/lib/transcript.mjs` and `questions.mjs`, so it reads Claude Code and Codex Transcripts, and finds a Claude Code Session's Transcript after it moved to another directory or Worktree. Additions:
      - **Tool calls:** entries with the tool name and a short argument.
      - **Questions:** entries with structured options and, once answered, the answer.
      - **Cursors:** `--after <cursor>` returns only newer entries. `--before <cursor> --limit <n>` pages back for "Show earlier".
      - **Contract** (agreed with the fork; as built in `dafilipaj/fleet` branch `lookout`, `docs/cli.md` "Messages"): `fleet --local messages --json [--after=<c> | --before=<c>] [--limit <n>] -- <target>`. Success is one JSON object: `ok`, `session_id`, `harness`, `transcript` (null before the first prompt), `entries`, `updated`, `has_more_before`, `has_more_after`, `cursor`. The top-level `cursor` is the one to poll with: the newest position plus a read hint, so it can move without new entries; it's null only for an empty conversation with no `--after`. Each entry has an opaque `cursor` (printable ASCII, at most 512 characters, no leading `-`), `role`, `kind` (`user`, `assistant`, `command`, `system`, `question`, `tool_call`), `ts` and `text` (Markdown for `assistant`); `assistant` adds `final`, `command` adds `name` and `args` (`command` and `system` have role `user`; `system` entries are Claude Code's task notifications, `text` their summary, and the only ones Fleet emits), `tool_call` adds `id`, `tool` and a `summary` of at most 120 characters (never output), and `question` adds `id`, `questions` (`question`, `header`, `multiSelect`, `options` of `label` and `description`), `status` (`pending`, `answered`, `declined`, `abandoned`: never answered and the conversation moved on) and `answer`: null while pending, `{declined: true}`, or `{answers, picked}` with one element per question (the recorded text, and the indexes of the options it picked; empty for a typed answer). `--after` answers also carry `updated`: older entries that changed since (a question answered, a reply that grew), to replace by cursor. Prompts typed while the agent is busy come last in every no-cursor and `--after` answer as the full current queue, `queued: true` with `q…` cursors that aren't positions. A Session with no Transcript yet is an empty conversation, not an error. Fleet never emits thinking, hook output, bookkeeping, sidechains or tool results. A failure exits 1 with `{ok: false, kind, error}` on stdout; kinds are `target_not_found`, `target_ambiguous`, `target_invalid`, `transcript_not_found` (a Claude Session without a session id), `harness_unsupported`, `cursor_invalid` (the Transcript was rewritten), `usage` and `io`.
      - **In Lookout:** every entry is type-checked and bounded (text 200,000 characters, a summary one line of 200, at most 10 questions of 20 options, every option kept in place so `picked` indexes hold, invalid indexes dropped); `system` entries are kept with their text bounded like any other, and unknown kinds are dropped (VIEW-1.3), and repeated cursors within one answer are kept once. Queued prompts are kept apart from the history: never buffered, trimmed, paged or used as a cursor. Cursors go to Fleet as `--after=<c>`, so one starting with `-` stays a value. Fleet's error text reaches the browser as one line of at most 200 characters, with token-like runs, credentials in URLs and `Authorization` values redacted, and tmux reworded (0001). An answer, poll or page, naming another Session or Harness than the one asked for is refused. A pid target gets the same fresh-list check as send and peek, reused for 5 s.
      - **Known gaps (fork):**
        - A Codex Session with no id on its command line (`codex resume --last` or the resume picker), whose process runs in another directory than its Transcript records, gets no Transcript and shows "No messages yet", not VIEW-1.8's note that the Transcript can't be found. Fleet pairs a Codex process with its Transcript by an id on its command line, else by the directory the Transcript records, and the Session's id comes only from that pairing. Sessions Lookout starts or resumes from History aren't affected: a start runs in the directory its Transcript records, and a resume passes the id (`codex resume -- <id>`).
        - A Claude Code Transcript filed under two project directories: Fleet takes the current directory's file, else the first one listed, not the newest.
        - Fleet names a project directory (`encode_cwd`) by turning only `/` and `.` into `-`, while Claude Code turns every character but a letter or digit into `-` (`/work/my_app` is filed under `-work-my-app`). So for a cwd with `_` or a space, Fleet's direct lookup misses and it falls back to scanning every project directory, which takes the first match.
    - **`fleet answer <target> …`** (VIEW-4.1–4.3). Ports the web app's AskUserQuestion answering and adds permission prompts. It checks that the screen still shows the prompt untouched before typing anything. Built in the fork (`lookout` 1f824eb, ce2bbe1); Lookout's use is under "Answering and stopping" below.
    - **`fleet keys <target> Escape|Enter|Up|Down`** (VIEW-4.4). Built in the fork (fe0740b).
- **Live updates.** Each tab's event stream gets an id in its snapshot; the tab says what it views, and whether its drawer is open, with `PUT /api/watch` (Origin and token, like every mutating route). When the stream closes, the server forgets it. The server follows only the Sessions some tab is viewing:
  - `fleet messages --after` every second, pushed over the existing SSE stream (VIEW-1.4). One feed per Session however many tabs view it, and every viewed Session is followed, Controllable or not (reading controls nothing):
    - The first call has no cursor: the latest 100 entries and the queue go to the tabs as a `reset`, with the cursor for "Show earlier". After it, `--after <top-level cursor> --limit 500` runs a second after the previous call ended, so calls never overlap. Each answer goes out as one `append`: new entries, `updated` entries (replaced by cursor, in the server's buffer and in the tab, with no reload) and the queue as it is now (replacing the old one); nothing is sent when none of them changed. `has_more_after` makes the next call start at once.
    - An empty conversation (a new Session) keeps polling without a cursor, but a `reset` goes out only when something changed, not every second.
    - A tab that starts viewing gets the feed's latest entries (it keeps up to 500) and queue at once, without a Fleet call. A feed no tab views is parked for 5 s: no new calls, and the one in flight finishes (Lookout can't cancel a run yet); viewed again, it carries on, so quick switching (A→B→A, holding j/k) never runs two calls for one Session. After 5 s it's dropped, once its call has ended.
    - `cursor_invalid` reloads without a cursor; its `reset` replaces what the tabs have, pages loaded with "Show earlier" included. `transcript_not_found` is a `missing` problem, checked every 5 s (VIEW-1.8: the pane says the Transcript can't be found; a Session that simply hasn't written one yet shows a quiet "No messages yet", as does a Codex Session Fleet can't pair, see Known gaps (fork)). Other failures keep the entries, show the reason and retry after 1 s, 2 s, then every 5 s.
    - Once Fleet no longer lists the Session, Fleet isn't asked again and nothing is cleared, so an ended Session's chat stays readable (VIEW-5.3); "Show earlier" is hidden then.

  - **Needs you**: Status is `needs-you`; the text adds Fleet's `waiting_for` when there is one.

With neither, from when Status turned `busy` (a turn with no prompt of yours, such as a background task); otherwise no time is shown. "12s", then "3m 07s", then "1h 02m".

It's a POST only because a batch doesn't fit a URL; it changes nothing, and the guard asks the token and Origin as for every POST. The body must hold 1–100 strings, else 400; the Session must be in the server's last `fleet list`, else 404. Each path is answered `{path, exists, absolute}` in the order asked. Not plain (control or format characters, `\p{Cc}` and `\p{Cf}`, which cover bidi controls and invisible characters; a `~`; a `:`; empty; over 1,024 characters): `exists: false`, never looked up. Otherwise it's resolved against the row's cwd (an absolute one only normalised), so `..` and `.` go, and `fs.stat` says whether it's a regular file (a symlink to one counts); nothing opens the file. - **Attachments (VIEW-9).** No Fleet change and no Building block ([0005](../../decisions/0005-building-blocks-live-outside-lookout.md)): a path is text, which `fleet send` types like any message (VIEW-3), and only a browser needs somewhere to put a file without a path.   - **Route:** `POST /api/attachments?name=<percent-encoded>` in `server/app.ts`, the body the file's raw bytes with `Content-Type: application/octet-stream`. It's a mutation, so the guard asks Lookout's Origin and the token as for every POST (0003). It isn't per Session: a copy belongs to none until you send its path. Before a byte is read: `name` missing, empty or over 1,024 characters → 400; another content type → 415; no `Content-Length` → 411; one over 25 MB (26,214,400 bytes) → 413. A body that runs past its length or the limit anyway is cut off, as `readBody` cuts off an oversized JSON body. The answer is `201 {path}`, the absolute path, nothing else. Each request carries one file and nothing ties it to a drop, so VIEW-9.8's 20 files a drop is enforced in the tab only; the server's limits are per file.
  - **Saving:** the attachments folder and the day folder (the server's local `YYYY-MM-DD`) are made with `mkdir -p`, mode `0700`, then each is opened with `O_DIRECTORY | O_NOFOLLOW` and set to `0700` through that handle, so a link in a folder's place is refused, never followed. A storage folder is trusted only as it is right before each use: `lstat` says a folder (not a link), the same one (`dev`, `ino`) as when it was made private, and its `realpath` is the attachments folder's own followed by its name. That check runs before the copy is created and before each `link`. The bytes stream into a hidden `.<random>.part` in it, opened with `wx` and `O_NOFOLLOW`, `0600`; before a byte is written, its `realpath` must lie in the day folder, so a folder swapped since the check fails the upload and its `.part` is unlinked. At the end it's linked to `<name>`, else `<stem>-2<ext>`, `-3`, … while `link` says `EEXIST` (VIEW-9.12), then the `.part` is unlinked. So an existing file is never opened for writing, and two uploads of one name can't take the same one. A failure or an aborted request unlinks the `.part`. `ENOSPC` → 507, "The disk is full, so <name> wasn't saved."; anything else → 500, "Lookout couldn't save <name>.". The route catches its own errors, so neither a name nor the file system's message (which holds the path) reaches the server's "request failed" log (VIEW-9.18).
  - **Pruning (VIEW-9.17):** at start, then a 24 h `setInterval` (unref'd). It reads the attachments folder with `withFileTypes` and enters only folders named `YYYY-MM-DD`, each only once it passes Saving's check (a folder, not a link, whose `realpath` is the attachments folder's followed by its name), right before its `readdir`. In each, `lstat` picks a regular file whose `mtimeMs` is 14 × 24 h old or more (a link, a folder or anything else stays). Right before its `unlink` the folder is checked again, as the same one (`dev`, `ino`), and the file `lstat`ed again: it goes only if it's still a regular file with the same `dev` and `ino`, still that old, so one touched or replaced meanwhile stays. A day folder whose date is 14 days back or more is checked once more and removed with `rmdir`, never recursively, so only once it's empty. An error skips that entry. When the attachments folder is missing or is itself a link, the run does nothing. Each run logs one line with counts only ("Pruned 12 attachments, 34 MB").
  - **In the tab, `web/src/lib/attachments.ts`:** `fromDrop(dataTransfer)` takes the `file://` URIs from `text/uri-list` (lines not starting with `#`; host empty or `localhost`; the path `decodeURIComponent`ed, absolute, with no control character), else `files`, telling a folder by `items[i].webkitGetAsEntry()?.isDirectory`; `fromPaste(clipboardData)` takes `files` only when `types` holds no `text/plain`, naming a nameless image (VIEW-9.10). `escapePath` (VIEW-9.6) and `insertion(text, start, end, paths)` (VIEW-9.5) are pure. `client.ts` gains `attach(file, name)`, a `fetch` with the token header and the `File` as the body; a drop's files upload at most 4 at a time.

### Key decisions

- **Transcript parsing lives in Fleet, not tb-session or Lookout**: Fleet already resolves the target and the Codex Transcript path (except the Known gaps (fork)), and has the parser in JS; Lookout stays a plain consumer. HIST's search stays in tb-session.
- **Answers go through Fleet commands that check the screen first**: typing into the wrong prompt is worse than not answering. This also works for Sessions on the iTerm2 backend.
- **The chat works for every Session; controls only for Controllable ones**: reading a Transcript doesn't control anything, and today most Sessions run in Orca. Codex: see Known gaps (fork).
- **Tool calls fold into one row per run**: you see what the agent touched without long tool-heavy turns drowning the text.
- **Enter sends**: it's what you type into the Claude Code and Codex terminals today; LAUNCH keeps ⌘Enter because its prompt sits in a form.
- **End Session shows for own-host Sessions as `fleet list` sees them, with Fleet's `host_shared` as the backstop**: the list can't count windows or panes, and adding that to `list` would be a Fleet change for a check `close` already makes. A refusal that explains itself costs one click; hiding the button from every tmux Session would make it useless.
- **The status line holds what describes the Session, the header what you act on**: the header stays short (title, Harness, Status, actions), and the line under the composer reads like a terminal's status line, where you look while typing.
- **The Subagents go on the status line only, not in the header or the chat (VIEW-8)**: they describe the Session, like its context and Effort; the header is for actions, and the chat's activity row speaks for the main thread, with VIEW-1.10's rules intricate and tested. Add a row state after live use if the status line isn't noticed.
- **Running in Busy's blue, done in Idle's grey, the words saying which (VIEW-8.1, 8.2)**: the colours are the ones the strip and the header's tag already use for working and finished, so the part reads at a glance; the text carries the state too, for anyone who can't tell the colours apart.
- **"Done" counts the Subagents that started and ended since your last prompt, and lasts until the next (VIEW-8.2)**: your prompt is where a piece of work starts, so the count is what this prompt set going; a Subagent's result that wakes the Session doesn't start a new one, and one started for an earlier prompt that ends now isn't this prompt's work.
- **The terminal preview opens on its own on Needs you**: a permission prompt's choices, and screens such as the trust prompt, exist only on the terminal screen, not in the Transcript.
- **Answers always pass `--allow-attached`**: the user is the only person who could be typing into these terminals, and Fleet still holds the Session's lock and checks the prompt is untouched; without it, every Session with a terminal attached would refuse.
- **A permission prompt's choices come from the screen (`answer --list`), not the Transcript**: the Transcript doesn't have them, and the screen's wording is what the terminal answers to. Its id goes back with `--prompt`, so the answer lands only on that prompt.
- **One click answers when nothing more can be picked**: a permission prompt, or one question with one choice. Several questions, multi-select, or typed text are picked, then submitted, so one stray click never sends half an answer.
- **When Fleet can't answer safely, no buttons**: one line says why and to answer in the terminal, which opens; nothing is retried, since a retry could land on the next prompt.
- **A question's buttons only once Fleet confirms its form**: a button Fleet will refuse is worse than none, so the reason shows before the click, from Fleet's code (`detail`), never its `error`, which may quote the screen. A question just asked gets 5 s for its form to be drawn before the line says the terminal doesn't show it: a read in that gap isn't a problem worth an alert. So does a run of failed reads, from its first: one slow `--list` (it times out at 4 s) mustn't flash an alert and the Esc button, or cost what you were typing. But only after a read that confirmed the form (or before any read in the spell): after a line, going quiet would itself flash, hiding the line and Esc and bringing the locked form back for a few seconds, so the line stays.
- **A send needs an empty input box, and a held one is never forced**: typing blind lost a message into `/usage`'s panel, and text after a restored prompt joins it; the person sees why and decides in the terminal, or with Esc.
- **Esc is Stop's twin for Needs you, not a general key pad**: one key, the same route, guard and refusals, shown only where Lookout offers no answer, so it never stands in for a choice the buttons make.
- **Stop sends one Esc, then waits**: in Claude Code a second Esc opens its rewind menu, so the button reads "Stopping…" until the Status leaves Busy, or for 10 s, and the server refuses a second Esc in the same Busy spell within 10 s whichever tab sends it. It shows only while Busy, and the server presses only if a fresh list still says Busy, since Esc on a prompt would decline it. No keyboard shortcut in v1: Esc already leaves the composer.
- **An answer carries the epoch of the read it answers, and the server keeps the last one per Session**: buttons in two tabs (or a reload) are the same buttons, and only the server sees both clicks. A click read before another tab's answer is refused with nothing typed; one answer per Session is typed at a time; after an uncertain outcome no tab answers that prompt again.
- **Answer and Stop use Fleet's exact targets and keep the interim pid guard**: every Fleet with `answer` and `keys` has `id:` and `pid:`, and the guard costs one list per answer.
- **A path is a link only once the server finds the file**: any pattern loose enough to catch `package.json` also catches `Node.js`, and VS Code opens an empty editor for a missing file. The pattern only picks candidates; the file system decides.
- **VS Code through a `vscode://file` link, not a server command**: the server never runs a shell for it, the link works from any tab, and Chrome's one-time prompt is the only cost.
- **Renaming goes through Fleet's `rename`, and the new title comes back through `fleet list`**: Fleet already picks the Harness's command, holds when typing is unsafe and keeps the Session host's name in step; the list already reaches every tab, so there's no second name to keep in Lookout and no Transcript to read.
- **Rename only an Idle Session**: Claude Code renames mid-turn, but Codex would queue `/rename` as a message and a prompt on screen would take it as an answer; Idle is the one state where both Harnesses take it at once.
- **The scroll bar blends through the standard `scrollbar-color`, not `::-webkit-scrollbar`**: Chrome prefers the standard properties when both are set, and they keep the platform's thumb and its hover behaviour.
- **The Effort switches through its own Fleet command, `fleet effort`, not `send "/effort …"`**: the two menus then share one tested path (the lock, the four checks, the confirmation, the Transcript's `Set … to` entry and its time), and Lookout shows nothing it can't confirm.
- **A new Requirement, VIEW-7, not more VIEW-6 criteria**: Requirements are capabilities (writing rule 1), VIEW-6's title names the model, and the Effort has its own command, levels and Known gaps, so `pnpm req-check --feature` and test names stay readable; what the menus share is referenced from VIEW-7.3, 7.6 and 7.9, not repeated.
- **Levels come from Fleet's `harness list` (`efforts`, `default_effort`), not a table in Lookout**: Fleet already reads `models_cache.json`, so Codex's come free and its Claude model table is hand-kept from the docs already; the launcher's effort picker and `spawn --effort` (Plan item 5) need the same lists, and Fleet owns the model lists they hang off (0005). The cost is one more field in the fork commit.
- **`fleet effort` and `harness list`'s levels land in one fork commit**: the levels are what the command's callers check against, and `spawn --effort` (Plan item 5) then reuses them; two commits would leave a command whose levels nothing can list.
- **`auto` isn't offered**: `/effort auto` clears the saved level for the model rather than setting one, and Fleet can never read `auto` back (a reply records the resolved level, and Dario's Transcripts hold only `high`, `medium` and `xhigh`), so the row could never be checked, and "from the next reply" would show a word the reply contradicts.
- **`max` is offered, with the menu's note that Claude Code applies it to this Session only**: it's a level the model runs at, Claude Code's docs list it for every model Fleet lists, and the note (VIEW-7.4) says what the other four do differently.
- **The menu alone closes the Backlog's "The Effort changes in the status line at once"; a `/effort` typed into the composer keeps VIEW-5.11's behaviour**: from a send Lookout can't tell whether Claude Code applied it (it asks nothing on the 5.5 models), asked, or was declined in the terminal, and a wrong level at once is the very thing the entry complained about. Typing `/effort` stays possible; the menu is the one-click route.
- **One "from the next reply" mark for a pending model and a pending Effort**: both go with the same reply (`model_at`), so two marks would say the same thing twice on one line.
- **The picked Effort shows from `model_at`, like the model**: both come from the same reply entry, so one time and one mark serve both, and nothing parses a command's output for state.

- **Attachments copy only what has no path, and insert a real path as is (VIEW-9.3, 9.4)**: Chrome never gives a page the path of a file dropped from Finder or pasted, so the Harness can only read a copy; a path VS Code hands over is the file itself, current, with nothing to prune.
- **Paths in the message, not files handed to the Harness**: Claude Code and Codex both read a file by its path, so it needs no Fleet change and the message stays text `fleet send` already types; their own image paste can't be driven through a terminal.
- **Copies go to `~/.lookout/attachments/<YYYY-MM-DD>/` and are inserted by absolute path (Dario's choice)**: a day's folder is easy to find and prune, and an absolute path reads the same from any Session's folder, resumed or moved.
- **Attaching is a new Requirement, VIEW-9, not more VIEW-3 criteria**: it's its own capability, with a server route and pruning, and keeps `pnpm req-check --feature` and test names readable.
- **Any type, up to 25 MB a file and 20 a drop (Dario, 2026-10-27)**: Lookout never opens, shows or runs a copy, so a type adds no risk, while a list would turn away logs, CSVs and archives an agent reads fine.
- **The server names the copy and picks its folder; the tab sends only bytes and a name**: a path taken from a request could write anywhere a Session reads from (0003).
- **A copy never overwrites a file**: a path already sent in a message must never come to name another file.
- **Pruning goes by each file's modification time, after 14 days (Dario's choice)**: a folder's date can never make a file saved a minute ago look old.
- **A message that starts with a path is a prompt (VIEW-9.7)**: Claude Code takes it so, and a dropped screenshot is most often the first thing in a message.
- **Send waits for uploads (VIEW-9.9)**: a message sent before its paths are in would leave without its files.
- **The upload is the raw file, one per request, not a multipart form**: no parser to add, the size is known before a byte is read, and the bytes stream straight to disk.
- **A paste that holds text stays text (Dario, 2026-10-27)**: spreadsheets put a picture of the cells beside their text, and pasting cells must keep working; a picture that should attach can be dropped instead.
- **A path's special characters get a backslash, not single quotes (Dario, 2026-10-27)**: it is what Terminal and iTerm2 write for a dragged file, which both Harnesses already get from a terminal drop; a plain path goes in as it is.
- **A drop lands anywhere on the Session view below the header (Dario, 2026-10-27)**: the chat is the bigger target, and the composer shows where the path will go.
- **Pruning runs when the server starts and every 24 h, by each file's modification time, never on a file younger than 14 days (Dario, 2026-10-27)**: pruning on each upload would walk the folder once per file.
