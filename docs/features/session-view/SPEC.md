# Session view

## Summary

The main pane for the Session selected in the sidebar. It shows the conversation as a chat built from the Transcript, a terminal preview, a composer to type into the Session, and buttons to answer what it's waiting on. Together with SIDE, it lets you follow and steer a Session without opening a terminal.

## Problem

Selecting a Session in SIDE shows only a placeholder. To see what an agent did, or to reply, you still have to find its terminal. When it Needs you, the question it's asking is only visible in that terminal.

## Requirements

### VIEW-1 Chat from the Transcript

The selected Session's conversation, read from its Transcript. Works for every Session Fleet lists, Controllable or not (Codex: see Known gaps (fork)).

- [x] VIEW-1.1 Your prompts and the agent's replies show in order, newest at the bottom. Replies are rendered as Markdown, code blocks included. Works for Claude Code and Codex Transcripts. (test)
- [x] VIEW-1.2 Consecutive tool calls fold into one row naming the tools and counts, e.g. "6 tool calls: Read ×3, Grep ×2, Bash" behind a chevron. Expanding it shows one line per call (tool plus a short argument). Tool output is never shown. (test)
- [x] VIEW-1.3 Thinking, hook output, bookkeeping entries, and subagent (sidechain) messages aren't shown. A Subagent's result (Claude Code's task notification, e.g. `Agent "Build" finished`) shows as a compact one-line row, smaller than messages and set apart from them. (test)
- [x] VIEW-1.4 A message the Harness writes appears within 2 s, without reloading. (manual)
- [x] VIEW-1.5 While you're at the bottom, the chat follows new messages. Once you scroll up it stays put and shows a "Jump to latest" button. (manual)
- [x] VIEW-1.6 Long Transcripts open fast: the latest messages load first, and "Show earlier" loads older ones. (test)
- [x] VIEW-1.7 A Claude Code Session's Transcript is found even after it moved into another directory or Worktree. (test)
- [x] VIEW-1.8 If no Transcript can be found, the pane says so; the terminal preview and composer still work. Codex: see Known gaps (fork). (test)
- [x] VIEW-1.9 A question the agent asked you (Claude Code's AskUserQuestion) shows in the chat with its options, and afterwards with the answer you gave. Each option has a box when several can be picked and a circle when one can, checked, or with a dot, once picked. (test)
- [x] VIEW-1.10 While the Session works on an answer, a "Working…" row with the time since your prompt (e.g. "Working… 12s") sits at the bottom of the chat. It appears the moment you send from the composer, under your message (VIEW-1.13). While the Session Needs you, it reads "Needs you" instead, with what it waits for when Status has it. It disappears once the reply is final and the Session is Idle, and never shows for an ended Session. (test)
- [x] VIEW-1.11 A narrow rail beside the chat's scroll bar has a Mark for each prompt you sent (a dot), Subagent result (a diamond) and question (a triangle), each at its entry's place in the chat's full height. Clicking a Mark scrolls to its entry, smoothly unless you prefer reduced motion; hovering or focusing it shows the entry's first line and time. `[` and `]` jump to the previous and next Mark when focus isn't in a text field. A jump counts as scrolling up (VIEW-1.5). Marks cover the loaded entries; while "Show earlier" is available, a Mark at the top loads the earlier page. The rail is hidden when there are no Marks, and when the chat is too narrow for it. (test)
- [x] VIEW-1.12 Every http(s) address in the chat is a link: in your prompts, in replies (inside code too), on tool-call lines, on Subagent result rows and in questions. A click opens it in a new browser tab with no referrer. The text reads and copies exactly as before, a link keeping its case under an uppercase header. Other schemes stay text. Exceptions: the permission prompt card and a question's answer buttons stay plain text, a bare IPv6 host in prose isn't linked, an address ends at a bidi control or an invisible character (a Markdown link holding one stays text), and Markdown's `mailto:` links still work. (test)
- [x] VIEW-1.13 A message you send from the composer shows in the chat at once, dimmed, above the "Working…" row (VIEW-1.10), until its copy from the Transcript reaches the chat and takes its place. Its copy is a prompt of yours, in the history or the queue, written at or after the send: first the one with its text, compared as the server sends it (line breaks as `\n`, a one-line message's tabs as spaces, trimmed) and as Fleet records a command (shell mode's `!cmd` as `! cmd`, a slash command's arguments one space after its name); for a message no copy's text matches, the first one left over, in send order, whatever its text. A slash command (`/…`) takes only a copy with its text, since some (`/usage`, `/status`) write nothing to the Transcript; while it waits, it goes once a prompt of yours that came after it reaches the chat (written at or after its send and not an earlier message's copy; a later message's copy counts), since the Harness takes input in order: it gets no line and doesn't open the Terminal preview. Claude Code's interrupt marker (`[Request interrupted by user…]`) is never a copy. A failed send (VIEW-3.4) takes it away. If no copy has come once the Session has been Idle for 30 s (the count runs only while it's Idle and the chat can show the message without a feed problem such as "Couldn't read new messages", and starts again each time it turns Idle, the chat can show it again or the problem clears), the message says, under it, that it hasn't reached the Transcript and to check the terminal (a slash command: that its result shows in the terminal, not as a problem), and the Terminal preview opens; from then on only a copy with its text takes its place, and it goes once a newer prompt of yours that isn't another message's copy reaches the chat, or a send from the composer succeeds. While there's no Transcript (VIEW-1.8), or before the chat has loaded, none shows, times out or opens the preview. None shows for an ended Session; they go when you select another Session, and stay when a Codex Session gets its session id. Only the tab that sent it shows it: other tabs show the copy once it arrives. (test)

VIEW-1.13 is covered by component tests that push the feed's events into the tab, with hand-made times; it's retagged `(e2e)` once the Fake Harnesses take prompts and write them into their Transcripts (TEST-1.4): a send to an Idle Session, one queued behind a Claude Code turn, one to a Busy Codex Session, and a second tab for "only the tab that sent it", which a component test can't show (each rendered tab has its own fake server).

## Non-goals

- A live, interactive terminal in the app (xterm.js); see [0001](../../decisions/0001-tmux-as-hidden-session-host.md).
- ANSI colours in the terminal preview.
- Tool output, images and attachments from the Transcript (an image shows as a placeholder).
- Subagent Transcripts.
- Buttons for prompts other than questions and permission prompts: the trust prompt, plan approval, login, update prompts, rate-limit dialogs. The terminal preview shows them; answer them in the terminal.
- Slash-command autocomplete, file mentions, attachments and voice in the composer.
- Editing, rewinding or forking a conversation.
- Searching inside the chat, and past Sessions (HIST).
- Renaming Sessions.
- Ending a Session that shares its Session host with other windows or panes, runs in iTerm2, or runs in another app (VIEW-5.8 says to close it in the terminal).
- Stopping a Session's Local servers when it ends.
- Opening the Session in iTerm2 (ITERM; the header leaves room for its button).
- A keyboard shortcut for Stop or the Esc button: Esc already leaves the composer (VIEW-3.6).
- Sending anyway when the input box isn't empty (Fleet's `--force`), clearing the box from Lookout, or showing what it holds (VIEW-3.7).
- Retrying a refused answer: the pane says to answer in the terminal instead (VIEW-4.3).
- Several Sessions side by side.
- Switching the model (VIEW-6): moving a Session to another vendor's models; switching a Codex Session's model (a Known gap until Codex 0.164's `/model <slug>` is installed); switching while Busy; a switch for this Session only (the picker's `s`); aliases such as `opus` or `opusplan`, `[1m]` variants and the "Default" entry; an extra row for a current model Fleet doesn't list; effort level and fast mode.

- One grid (SIDE-8): the header is the main pane's cell in the shell's header row, so its bottom line continues the Filter bar's and History's. The composer and status line are its cell in the dock row, so the line above the composer continues the line above the usage panel. Chat and Terminal row sit between the two. A Session that isn't Controllable, or has ended, puts its banner where the composer goes, with the status line under it. The header is always one line, so the header row keeps its height whichever Session is selected; what a Needs you Session waits for shows in the chat's Needs you row (VIEW-1.10).
- Every main-pane view has a header cell of the same height: nothing selected (empty), Settings (Back and the title), a past Session (HIST-3.3), a start under way (LAUNCH-4.6), loading. Views without a composer run their content to the bottom.
- Short windows: the Terminal preview gives way first, shrinking toward its Terminal row; the chat keeps at least 96 px; the composer grows to at most 12rem or 20% of the window's height, whichever is less, and scrolls past that.

- Your message on its way (VIEW-1.13): your prompt's bubble at 60% opacity, headed "You" without a time, where the next prompt would go: after the queue, above a permission card and the Working row. A screen reader hears "sending" after "You". The copy from the Transcript takes its place in the same spot and may read slightly differently (shell mode's `!git status` as `! git status`). In an empty conversation it replaces "No messages yet". Before the chat has loaded, and while there's no Transcript, it doesn't show. One whose copy didn't come keeps its dimmed bubble, without "sending", over one line as for an answer Lookout can't be sure of (VIEW-4.3): "It hasn't reached the Transcript, so the Session may not have taken it. Check the terminal.", with "Show terminal" while the preview is closed. A slash command's line isn't a warning: "This command's result shows in the terminal.", in muted text, read out politely rather than as an alert, with "Show terminal" too. The preview opens when the line appears. A newer prompt of yours (typed in the terminal, say) takes the bubble away, so it never sits under that prompt's turn; a slash command's bubble still "sending" goes the same way, with no line. While the chat shows a feed problem, a bubble stays "sending".
- `[actions]`: Stop (VIEW-4.4) while the Session is Busy, or Esc (VIEW-4.5) while it Needs you with no answer buttons, then End Session (VIEW-5.6); ITERM's button joins them there.
- Permission prompt (VIEW-4.2): a card at the bottom of the chat, above the Needs you row, styled like a pending question: "<Harness> asks", the prompt's title and the lines it shows (the command or file, monospace, scrolling past 10 lines), then one button per choice, stacked, in the terminal's wording, each led by its number in the terminal. A click answers at once; while Fleet types, the buttons are disabled and "Answering…" shows. Once answered, the card goes until the next read of the screen. If another tab answered it first, the click says so ("already answered from another tab") until the next read, which brings the next prompt's buttons. If another tab was answering it, the click says that ("Another tab is answering…") until the next read: when that answer typed nothing, the read brings the same buttons back.
- Question (VIEW-4.1): while it's the one the Session waits on, the chat's question card turns its options into buttons, with a circle for one choice and a box for several, and a "Type something…" field under each question. Until the first read of the screen reaches the tab (about a second), the buttons and field are disabled. One question with one choice answers on the click. Several questions, a multi-select one, or typed text: pick, then Submit (disabled until every question has an answer; Enter in a field submits too). Typing replaces a one-choice question's pick and joins a multi-select one's, as in the terminal. Once sent, it reads "Sent. Waiting for the Session…" until the chat shows the answer. Pasted text is cleaned as it's typed: a tab becomes a space, other control characters go. An answer the server can't take as written says why inside the form, which keeps the text to fix; no row is left empty under a one-click question. A question that can't be answered from here (another app, Codex, not Needs you, a permission prompt on screen) keeps its read-only options and says "Answer it in the terminal."
- When Lookout won't answer (VIEW-4.3): the buttons are replaced by one line saying why, in plain words by kind, and to answer in the terminal (for an uncertain outcome, from any tab, and for a lost connection to Lookout: it may have been answered; check the terminal). The prompt's text stays above it. A refusal after a click opens the Terminal preview; otherwise, while the preview is closed, the line offers "Show terminal". Nothing is retried.
- Stop (VIEW-4.4): an outline button with a stop icon. After a click it reads "Stopping…", disabled, until the Status leaves Busy or 10 s pass. If Stop fails, why sits beside it, cut to fit the header's one line, with the whole text in a bubble under the header on hover or focus (it moves nothing and stays inside the pane). Stop's tooltip and description carry it too. A lost connection says Esc may have been pressed and opens the Terminal preview.
- Esc (VIEW-4.5): Stop's outline button in Stop's place, labelled "Esc", with a stop-like icon (lucide's `OctagonX`). Its tooltip: "Press Esc in the Session: closes a panel or menu, or cancels the prompt". After a click it reads "Pressing Esc…", disabled, until the Status leaves Needs you or 10 s pass. Its error, and a lost connection, show as Stop's do (below), and the narrow-header rules treat it as Stop.
- A held send (VIEW-3.7): its message sits above the box, where a failed send's error does, and the text stays in the box. While Esc shows, "no input box" adds "The Esc button at the top of the pane does that." and "a prompt waiting" adds "Or cancel it with the Esc button at the top of the pane."
- The header's one line at any width, with the buttons always whole: only they never shrink. Stop's error gets only the room left over (at least 3rem), the title gives way next, down to an ellipsis, and a narrow header drops the Harness's name and the Status's age (below 32rem), then the buttons' words (below 26rem; they stay the buttons' names and tooltips), then Stop's error (below 20rem; Stop turns the error's colour and keeps it as its tooltip and description). Narrower still, the rest of the line is cut off before the buttons.
- Status line (VIEW-5.5): one line in the monospace font, the parts separated by `·`. At narrow widths each part truncates with `…`; hovering shows the whole line, and the Worktree or branch on its own. The context usage reads in the line's colour up to 40%, amber (the warning colour) above 40% and red above 60% (the warning and danger tokens, `needs-you-text` and `destructive`, which have light and dark values); 40% and 60% exactly keep the lower colour.
- Model switch (VIEW-6): the model's name is a ghost button with a chevron, the same size as the line's text. The menu opens upward, above the status line: one radio item per model (label, with its id dimmed), the current one checked, and under them one muted line, "Also becomes the default for new Claude Code Sessions." While switching, the name reads "Switching…". After, the new model shows with "· from the next reply" in muted text until the next reply reaches the Transcript. An error sits beside the name, cut to fit the line, with the whole text in its tooltip (as Stop's error does in the header).
- End Session (VIEW-5.6): the dialog names the Session, says its Harness is asked to exit and its Session host closed, and that its chat stays readable and History can resume it. Buttons: Cancel and End Session (destructive). While Fleet works, End Session reads "Ending…".

- Status tag (VIEW-5.9): a pill with the Status and its age, tinted in the Status's colour with text in its darker (light mode) or lighter (dark mode) shade: Needs you amber, Busy blue, Idle and Unknown grey. "Ended" is muted grey. The age is in the tag's colour at normal weight: dimmed to 70%, as it was, it read at about 3.2:1 in light mode.
- Loading: a skeleton for the chat; the header shows at once from SIDE's data.
- Errors: Transcript missing (VIEW-1.8), send failed (VIEW-3.4), answer refused (VIEW-4.3), and preview failed (the drawer says so and keeps retrying).

## Technical approach

- **Building blocks.** Fleet's CLI with `--json` ([0004](../../decisions/0004-fleet-cli-as-session-layer.md)), from the fork `dafilipaj/fleet` ([0006](../../decisions/0006-run-a-fork-of-fleet.md)). *Target* is the `session_id` prefix or the pid.
  - **Available now** (checked in Fleet 38a461c's source):
    - `fleet --local send --json --require-empty -- <target> <text>` types the text and submits it (VIEW-3). Text with line breaks goes in as a tmux paste, so they survive; a single line is typed. The `--` keeps text that starts with `-` from being read as an option. Lookout's target is the full `session_id`, or the pid for a Codex Session without one.
    - **Held sends (VIEW-3.7; fork `lookout` e0d4612, docs/cli.md "Sending").** Under the Session's typing lock, `send` reads the input box off the screen once and types only into an empty one. Without `--require-empty`, a box it can't find or read is typed into anyway, with a warning: that's how `/usage`'s panel, which only Esc closes, took Dario's next message. So Lookout always passes `--require-empty`, never `--force`. A replaced message stays in the list, hidden, while another still shows, so its copy is never taken a second time; the list empties once all are replaced. Matching runs on the whole chat each time, not on what each event adds, so a reset (a Codex id change, `cursor_invalid`) or a prompt moving from the queue into the history changes nothing.

The Harness takes input in order, so by then it has handled the command and nothing more will come for it: `/status` writes nothing, and Codex's `/init` writes a prompt with other text, which a slash command never takes by time. It goes without a line and doesn't open the preview: the prompt after it shows the Session took it. An earlier message's copy doesn't count, since that message came first. A command with nothing after it keeps the timeout and its line. A copy written late (`/compact`'s, after the summary) then shows in its own place. It's a step of its own in `settleEchoes`, after matching and before the timeout.

### Key decisions

- **Transcript parsing lives in Fleet, not tb-session or Lookout**: Fleet already resolves the target and the Codex Transcript path (except the Known gaps (fork)), and has the parser in JS; Lookout stays a plain consumer. HIST's search stays in tb-session.
- **Answers go through Fleet commands that check the screen first**: typing into the wrong prompt is worse than not answering. This also works for Sessions on the iTerm2 backend.
- **The chat works for every Session; controls only for Controllable ones**: reading a Transcript doesn't control anything, and today most Sessions run in Orca. Codex: see Known gaps (fork).
- **Tool calls fold into one row per run**: you see what the agent touched without long tool-heavy turns drowning the text.
- **Enter sends**: it's what you type into the Claude Code and Codex terminals today; LAUNCH keeps ⌘Enter because its prompt sits in a form.
- **End Session shows for own-host Sessions as `fleet list` sees them, with Fleet's `host_shared` as the backstop**: the list can't count windows or panes, and adding that to `list` would be a Fleet change for a check `close` already makes. A refusal that explains itself costs one click; hiding the button from every tmux Session would make it useless.
- **The status line holds what describes the Session, the header what you act on**: the header stays short (title, Harness, Status, actions), and the line under the composer reads like a terminal's status line, where you look while typing.
- **The terminal preview opens on its own on Needs you**: a permission prompt's choices, and screens such as the trust prompt, exist only on the terminal screen, not in the Transcript.
- **Answers always pass `--allow-attached`**: the user is the only person who could be typing into these terminals, and Fleet still holds the Session's lock and checks the prompt is untouched; without it, every Session with a terminal attached would refuse.
- **A permission prompt's choices come from the screen (`answer --list`), not the Transcript**: the Transcript doesn't have them, and the screen's wording is what the terminal answers to. Its id goes back with `--prompt`, so the answer lands only on that prompt.
- **One click answers when nothing more can be picked**: a permission prompt, or one question with one choice. Several questions, multi-select, or typed text are picked, then submitted, so one stray click never sends half an answer.
- **When Fleet can't answer safely, no buttons**: one line says why and to answer in the terminal, which opens; nothing is retried, since a retry could land on the next prompt.
- **A send needs an empty input box, and a held one is never forced**: typing blind lost a message into `/usage`'s panel, and text after a restored prompt joins it; the person sees why and decides in the terminal, or with Esc.
- **Esc is Stop's twin for Needs you, not a general key pad**: one key, the same route, guard and refusals, shown only where Lookout offers no answer, so it never stands in for a choice the buttons make.
- **Stop sends one Esc, then waits**: in Claude Code a second Esc opens its rewind menu, so the button reads "Stopping…" until the Status leaves Busy, or for 10 s, and the server refuses a second Esc in the same Busy spell within 10 s whichever tab sends it. It shows only while Busy, and the server presses only if a fresh list still says Busy, since Esc on a prompt would decline it. No keyboard shortcut in v1: Esc already leaves the composer.
- **An answer carries the epoch of the read it answers, and the server keeps the last one per Session**: buttons in two tabs (or a reload) are the same buttons, and only the server sees both clicks. A click read before another tab's answer is refused with nothing typed; one answer per Session is typed at a time; after an uncertain outcome no tab answers that prompt again.
- **Answer and Stop use Fleet's exact targets and keep the interim pid guard**: every Fleet with `answer` and `keys` has `id:` and `pid:`, and the guard costs one list per answer.
